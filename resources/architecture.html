The Idempotency Engine

A dev-time memory for errors, problems, and decisions.
Architecture Spec · v1 (Final) · collapse · discriminate · relate · version

0 What this system is

A local RAG that accumulates what you and your agents learn while developing. When an error appears, the system either returns a known solution or records a new entry for future lookup.

Not observability

No alerting, no suppression, no on-call. It is a memory. It runs when you query it, not when something fires.

Case 1

Discriminate

Same text, different cause → different fixes. Anchor groups by shape; variants discriminate by context.

Case 2

Relate

Different text, same fix. Hashing collapses structurally similar; linking bridges distant wordings.

Case 3b

Version

Same text, same context, fix changes over time. Solutions are versioned; one current per variant.

Three entry kinds

KindWhat it is
errorA failure — log line, stack trace, command output
problemA statement of what you're working on — "hibernation fails on wake"
decisionA recorded choice — "chose pipewire over pulseaudio"

All three share the same schema, pipeline, and retrieval surface.

Core design principles

One API, many clients. The C# Ingest API is the source of truth. Watcher, MCP, CLI, and any future dashboard are clients. MCP is the agent adapter — not a gateway.

Idempotency is layered. HTTP event IDs, unique constraints, advisory lock, optimistic checks, and peek-before-embed. Each layer catches what the previous missed.

3.2 · The eight tables, explained

ProcessedIncidents
Entity: an anchor — a generalized error shape
Why it exists: this is the collapse layer. Many raw lines that mean the same thing become one row here. Identity is (kind, domain, shape_hash, shape_version).
Holds error_embedding for cross-anchor linking, and shape_template for humans.
every raw line would be its own row. Retrieval would return hundreds of duplicates for the same underlying issue.
IncidentVariants
Entity: a variant — a specific cause under an anchor
Why it exists: this is the discriminate layer. Same error text, different root cause → different variants. Identity is (incident_id, context_fingerprint).
Holds context_embedding for semantic matching, occurrence_count for volume, status for review, merged_by_embedding for audit.
one anchor would carry one solution. You couldn't distinguish "connection refused because service is down" from "connection refused because firewall is blocking".
VariantSolutions
Entity: a solution — a fix, versioned
Why it exists: this is the versioning layer. The same variant can have had multiple solutions over time. One row per solution ever recorded; the current one is the row with superseded_at IS NULL.
Holds superseded_reason and verified.
you'd overwrite solutions and lose history. No way to know the old fix stopped working or why.
IncidentLinks
Entity: a relation — "these anchors are probably the same issue"
Why it exists: this is the relate layer. Different wordings of the same underlying problem become different anchors. The link bridges them.
Kind is suggested, confirmed, or rejected. Auto-linking is within-kind only; cross-kind is explicit.
a query for one wording would miss the other. Four disconnected anchors when they're actually one issue.
Domains
Metadata: a problem area namespace
Why it exists: every anchor belongs to exactly one domain (hibernation, postgres, sound). Domain is part of the anchor's identity, so the same error text in two domains is two different anchors.
Holds per-domain shape_version. Bump the rules, get new anchors without invalidating old ones.
no way to scope rules, rate limiting, or retrieval by problem area.
SystemConfig
Metadata: global key-value settings
Why it exists: holds things that aren't per-domain and don't deserve their own table: active_embedding_model, lock_budget_ms, linker_last_checkpoint.
The checkpoint especially needs to live in the DB so a restart doesn't lose the sweep's place.
scattered config in env vars or hardcoded constants.
ProcessedIngests
Support: the idempotency gate
Why it exists: retries. If the watcher POSTs a batch, the API commits, and the response is lost, the watcher retries. Without this table, the retry would double-count occurrence_count.
Every count increment is paired with an insert here in the same transaction.
the system's core guarantee — remember things accurately — is violated the moment a network hiccup causes a retry.
SolutionFailures
Support: append-only failure log
Why it exists: "I tried this solution and it didn't work." Records a specific observation about a specific solution on a specific variant.
Does not automatically supersede the solution — that's a human/agent decision. Provides a trail for revising solutions later.
solutions with no track record. A fix that's failed five times would look as good as one that's worked fifty times.

3.3 · What is an anchor?

An anchor is a generalized error message — but "generalized" is a specific, rule-driven process, not an intuition. An anchor is the message after the domain's rules have stripped its variables.

The anchor as a container
ANCHOR — ProcessedIncidents
"connection refused"
kind=error · domain=postgres · shape_hash=a3f... · shape_version=v1
VARIANT
{host: db-01, user: app}
systemctl start postgres
VARIANT
{host: db-01, firewall: on}
ufw allow 5432
VARIANT
{host: db-02, port: 5433}
fix DB_PORT env

What an anchor is not

  • Not the raw error line. That's in raw_text, only present in the batch payload, never stored.
  • Not the specific occurrence. That's a variant.
  • Not a solution. Solutions attach to variants, not anchors.
  • Not a link. That's a separate row connecting two anchors.

Why "anchor" and not "error shape"

Because it's where things anchor to. Variants anchor to it. Links anchor to it. Embeddings anchor to it. The whole system pivots around this generalized statement as the primary organizing entity — it's the container, not the content.

Anchors can be errors, problems, or decisions

Because kind exists, an anchor can represent an error ("connection refused"), a problem ("hibernation fails on wake"), or a decision ("chose pipewire over pulseaudio"). The generalization rules differ, but the shape of the entity is the same: a canonical string that things cluster around.

Schema

-- Idempotency gate: one row per processed observation
CREATE TABLE ProcessedIngests (
    event_id      TEXT PRIMARY KEY,
    processed_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Domains registry: holds per-domain shape_version
CREATE TABLE Domains (
    name           TEXT PRIMARY KEY,
    description    TEXT,
    shape_version  TEXT NOT NULL DEFAULT 'v1',
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Anchors: one per (kind, domain, shape_hash, shape_version)
CREATE TABLE ProcessedIncidents (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    kind              TEXT NOT NULL
        CHECK (kind IN ('error','problem','decision')),
    domain            TEXT NOT NULL REFERENCES Domains(name),
    shape_hash        TEXT NOT NULL,
    shape_version     TEXT NOT NULL,
    shape_template    TEXT NOT NULL,
    origin            TEXT NOT NULL
        CHECK (origin IN ('watcher','agent','human','dashboard')),
    error_embedding   VECTOR(384) NOT NULL,
    embedding_model   TEXT NOT NULL,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (kind, domain, shape_hash, shape_version)
);

CREATE INDEX idx_incidents_embedding
    ON ProcessedIncidents
    USING hnsw (error_embedding vector_cosine_ops);

-- Variants: one row per (incident_id, context_fingerprint)
-- A variant is a SEMANTIC CAUSE GROUP.
CREATE TABLE IncidentVariants (
    id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    incident_id         UUID NOT NULL REFERENCES ProcessedIncidents(id) ON DELETE CASCADE,
    context_fingerprint TEXT NOT NULL,
    context_embedding   VECTOR(384) NOT NULL,
    embedding_model     TEXT NOT NULL,
    context_json        JSONB NOT NULL,
    context_sample      TEXT NOT NULL,
    status              TEXT NOT NULL DEFAULT 'active'
        CHECK (status IN ('active','needs_review')),
    verified            BOOLEAN NOT NULL DEFAULT false,
    merged_by_embedding BOOLEAN NOT NULL DEFAULT false,
    occurrence_count    BIGINT NOT NULL DEFAULT 1,
    version             BIGINT NOT NULL DEFAULT 1,
    first_seen_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_seen_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (incident_id, context_fingerprint)
);

-- Solutions: versioned. One current per variant.
CREATE TABLE VariantSolutions (
    id                 UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    variant_id         UUID NOT NULL REFERENCES IncidentVariants(id) ON DELETE CASCADE,
    text               TEXT NOT NULL,
    recorded_by        TEXT,
    recorded_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    superseded_at      TIMESTAMPTZ,
    superseded_reason  TEXT,
    verified           BOOLEAN NOT NULL DEFAULT false
);

CREATE UNIQUE INDEX one_current_solution_per_variant
    ON VariantSolutions (variant_id)
    WHERE superseded_at IS NULL;

Semantics worth stating

  • occurrence_count counts observations assigned to this semantic variant — not unique context fingerprints. Multiple fingerprints may fold into one variant.
  • version on IncidentVariants is for user-facing writes only. Ingest count increments do not bump it.
  • origin is who produced the entry. Transport is request metadata, not stored.
  • merged_by_embedding marks variants auto-folded from a fingerprint miss.

5 The critical section

Peek first, embed conditionally, lock only on insert, idempotency-gate every write.

The rule

Lock only when an INSERT might happen. Re-check only what you might INSERT. Updates to known rows are atomic — no lock, no re-check, no re-embed. Idempotency insert lives in the same transaction as the count increment it gates.

CASE A
Anchor exists. All fingerprints hit. Pure repeat.

embedno
re-checkno
~5msfast path

6 Canonicalization & shape hashing

rules:
  - pattern: "/dev/sd[a-z]"
    replace: "<DEV>"
  - pattern: "pid [0-9]+"
    replace: "pid <PID>"
shape_string = apply_rules(canonical_error_line)
             | canonical_error_line   -- if no rule matches
shape_hash   = sha256(shape_string)

Same input + same rules → same hash, always. shape_version is per-domain — it lives on Domains.shape_version. Bumped when a domain's rule set changes.

Dual-layer design

Deterministic hashing collapses structurally similar text into anchors. Semantic linking bridges anchors that are textually distinct but conceptually related. Both layers are necessary; neither alone is sufficient.

Fingerprint vs. variant

A context fingerprint is an exact identifier. A variant is a semantic cause group. Multiple fingerprints may map to one variant when the KNN gate finds them close enough.

8 Solution versioning (Case 3b)

BEGIN;

UPDATE VariantSolutions
SET superseded_at = now(),
    superseded_reason = $reason
WHERE variant_id = $variant_id
  AND superseded_at IS NULL
  AND id = $expected_solution_id;

rows = ROW_COUNT;
IF rows = 0 AND $expected_solution_id IS NOT NULL:
    ROLLBACK;
    RETURN 409 CONFLICT;

INSERT INTO VariantSolutions (variant_id, text, recorded_by, verified)
VALUES ($variant_id, $text, $recorded_by, false);

COMMIT;

9 Linking (Case 2)

Runs post-commit. Triggered by NOTIFY anchor_created. Backed up by a periodic sweep so missed notifications don't silently orphan anchors.

Fast path — NOTIFY

On notification: fetch anchor, rate-gate per domain, ANN within kind, insert suggested links.

Backstop — periodic sweep

Every 5 minutes: find anchors created since last checkpoint with no outgoing link, process them the same way, advance the checkpoint.

14 Invariants

  1. 01HTTP idempotency. Every observation has a stable event_id.
  2. 02Determinism. shape_hash is a pure function of (shape_string, shape_version).
  3. 03Deterministic batch order. Samples sorted by context_fingerprint.
  4. 04Anchor uniqueness. One anchor per (kind, domain, shape_hash, shape_version).
  5. 05Variant uniqueness. One row per (incident_id, context_fingerprint).
  6. 06One current solution. Partial unique index.
  7. 07Solution concurrency. Conditional supersede + partial unique index.
  8. 08Bounded critical section. Lock budget 2,000ms.
  9. 09Lock only on insert. Fast path (Case A) takes no advisory lock.
  10. 10Post-commit notify. NOTIFY only after COMMIT.
  11. 11Linker backstop. Periodic sweep processes missed anchors.
  12. 12Cross-model suppression. KNN and linking compare same-model vectors only.
  13. 13One API, many clients. MCP is not in the path of any non-agent client.
  14. 14Embedding is a candidate signal. Fingerprint hits are authoritative.

17 What this system is not

  • Not observability. No alerting, no on-call dashboards.
  • Not a log store. Stores shapes, contexts, solutions — not raw log lines.
  • Not real-time. 5s batch + async linker + periodic sweep.
  • Not multi-user. Shared knowledge is within one machine.
  • Not distributed. One Postgres, one API, one watcher.
Summary

Four mechanisms: collapse (hashing), discriminate (context + embedding), relate (linking), version (solutions).

Two axes: kind and domain. Everything else is context or config.

Eight tables: four model entities (anchor, variant, solution, link), two are metadata (domain, config), one gates ingestion, one logs failures.

One API, many clients. MCP is the agent adapter — not a gateway.
