The Idempotency Engine

A dev-time memory for errors, problems, and decisions.
Architecture Spec · v1 (Final) · collapse · discriminate · relate · version

0 What this system is

A local RAG that accumulates what you and your agents learn while developing. When an error appears, the system either returns a known solution or records a new entry for future lookup.

Not observability

No alerting, no suppression, no on-call. It is a memory. It runs when you query it, not when something fires.

Case 1

Discriminate

Same text, different cause → different fixes. Anchor groups by shape; variants discriminate by context.

Case 2

Relate

Different text, same fix. Hashing collapses structurally similar; linking bridges distant wordings.

Case 3b

Version

Same text, same context, fix changes over time. Solutions are versioned; one current per variant.

Three entry kinds

KindWhat it is
errorA failure — log line, stack trace, command output
problemA statement of what you're working on — "hibernation fails on wake"
decisionA recorded choice — "chose pipewire over pulseaudio"
Core design principles

One API, many clients. The C# Ingest API is the source of truth. Watcher, MCP, CLI, and any future dashboard are clients. MCP is the agent adapter — not a gateway.

Idempotency is layered. HTTP event IDs, unique constraints, advisory lock, optimistic checks, and peek-before-embed. Each layer catches what the previous missed.

Two axes: kind and domain. Everything else is context or config.

Lookup is a cascade — exact → variant KNN → anchor ANN. Each level prunes the next.

2 The three cases, illustrated

Case 1 — Same text, different cause

error: connection refused
   └── ANCHOR (kind=error, domain=postgres)
         ├── variant: service not started  → solution: systemctl start postgres
         ├── variant: firewall blocking    → solution: open port 5432
         └── variant: wrong port in config → solution: fix DB_PORT env

Case 2 — Different text, same fix

"Stored proc A not present"  ─┐
"Stored proc B not present"  ─┴─► ANCHOR A ("Stored proc <VAR> not present")
                                        │
                                        │ suggested link
                                        ▼
"Procedure Z does not exist" ────► ANCHOR B ("Procedure <VAR> does not exist")
Case 2 has two paths

At lookup time — when the wording differs enough to produce a new shape_hash, the lookup cascade's anchor-level ANN surfaces the related anchor's solution immediately.

At ingest time — if the new wording is ingested, the linker creates a persistent suggested link between the two anchors.

Both paths use the same embedding threshold. Both are needed: lookup for immediate recall, links for persistent relationship tracking.

Case 3b — Fix changes over time

VARIANT (hibernation fails on wake, kernel 6.8, nvidia)
   ├── Solution A  (superseded 2024-03, reason: kernel update)
   ├── Solution B  (superseded 2024-08, reason: nvidia driver fix)
   └── Solution C  (CURRENT)

3.2 · The eight tables, explained

ProcessedIncidents
Entity: an anchor — a generalized error shape
Why it exists: the collapse layer. Many raw lines that mean the same thing become one row. Identity is (kind, domain, shape_hash, shape_version). Holds error_embedding for cross-anchor linking and lookup ANN.
every raw line would be its own row. Retrieval returns hundreds of duplicates for the same issue.
IncidentVariants
Entity: a variant — a specific cause under an anchor
Why it exists: the discriminate layer. Same error text, different root cause → different variants. Identity is (incident_id, context_fingerprint). Holds context_embedding, occurrence_count, status, merged_by_embedding.
one anchor would carry one solution. You couldn't distinguish "connection refused because service is down" from "connection refused because firewall is blocking".
VariantSolutions
Entity: a solution — a fix, versioned over time
Why it exists: the versioning layer. One row per solution ever recorded; the current one is the row with superseded_at IS NULL (partial unique index). Holds superseded_reason and verified.
you'd overwrite solutions and lose history. No way to know the old fix stopped working or why.
IncidentLinks
Entity: a relation — "these anchors are probably the same issue"
Why it exists: the relate layer. Different wordings of the same underlying problem become different anchors. The link bridges them. kind is suggested, confirmed, or rejected.
the persistent relationship graph would be missing. Lookup ANN still finds related anchors, but you couldn't browse them.
Domains
Metadata: a problem area namespace
Why it exists: every anchor belongs to exactly one domain. Domain is part of the anchor's identity. Holds per-domain shape_version.
no way to scope rules, rate limiting, or retrieval by problem area.
SystemConfig
Metadata: global key-value settings
Why it exists: holds active_embedding_model, lock_budget_ms, linker_last_checkpoint. The checkpoint must be durable so a restart doesn't lose the sweep's place.
scattered config in env vars or hardcoded constants.
ProcessedIngests
Support: the idempotency gate
Why it exists: retries. Every count increment is paired with an insert here in the same transaction. On duplicate event_id, the bump is skipped.
Not a lookup table. Lookup queries the anchor and variant tables, which are never deleted.
the core guarantee — remember things accurately — is violated the moment a network hiccup causes a retry.
SolutionFailures
Support: append-only failure log
Why it exists: records when a specific solution was attempted and failed. Does not automatically supersede the solution.
solutions with no track record.

3.3 · What is an anchor?

An anchor is a generalized error message — but "generalized" is a specific, rule-driven process. An anchor is the message after the domain's rules have stripped its variables.

The anchor as a container
ANCHOR — ProcessedIncidents
"connection refused"
kind=error · domain=postgres · shape_hash=a3f... · shape_version=v1
VARIANT
{host: db-01, user: app}
systemctl start postgres
VARIANT
{host: db-01, firewall: on}
ufw allow 5432
VARIANT
{host: db-02, port: 5433}
fix DB_PORT env

What an anchor is not

  • Not the raw error line (that's raw_text, never stored).
  • Not the specific occurrence (that's a variant).
  • Not a solution (solutions attach to variants).
  • Not a link (that's a separate row connecting two anchors).

Why "anchor": because it's where things anchor to. Variants anchor to it. Links anchor to it. Embeddings anchor to it. Anchors can be errors, problems, or decisions — the kind field distinguishes them.

3.5 · Schema

CREATE EXTENSION IF NOT EXISTS vector;

-- Idempotency gate: one row per processed observation
CREATE TABLE ProcessedIngests (
    event_id      TEXT PRIMARY KEY,
    processed_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_ingests_processed_at
    ON ProcessedIngests (processed_at);

-- Domains registry: holds per-domain shape_version
CREATE TABLE Domains (
    name           TEXT PRIMARY KEY,
    description    TEXT,
    shape_version  TEXT NOT NULL DEFAULT 'v1',
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Anchors: one per (kind, domain, shape_hash, shape_version)
CREATE TABLE ProcessedIncidents (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    kind              TEXT NOT NULL
        CHECK (kind IN ('error','problem','decision')),
    domain            TEXT NOT NULL REFERENCES Domains(name),
    shape_hash        TEXT NOT NULL,
    shape_version     TEXT NOT NULL,
    shape_template    TEXT NOT NULL,
    origin            TEXT NOT NULL
        CHECK (origin IN ('watcher','agent','human','dashboard')),
    error_embedding   VECTOR(384) NOT NULL,
    embedding_model   TEXT NOT NULL,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (kind, domain, shape_hash, shape_version)
);

CREATE INDEX idx_incidents_kind_domain
    ON ProcessedIncidents (kind, domain);
CREATE INDEX idx_incidents_domain_created
    ON ProcessedIncidents (domain, created_at);
CREATE INDEX idx_incidents_embedding
    ON ProcessedIncidents
    USING hnsw (error_embedding vector_cosine_ops);

-- Variants: one row per (incident_id, context_fingerprint)
-- A variant is a SEMANTIC CAUSE GROUP.
-- Multiple fingerprints may map to one variant.
CREATE TABLE IncidentVariants (
    id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    incident_id         UUID NOT NULL REFERENCES ProcessedIncidents(id) ON DELETE CASCADE,
    context_fingerprint TEXT NOT NULL,
    context_embedding   VECTOR(384) NOT NULL,
    embedding_model     TEXT NOT NULL,
    context_json        JSONB NOT NULL,
    context_sample      TEXT NOT NULL,
    status              TEXT NOT NULL DEFAULT 'active'
        CHECK (status IN ('active','needs_review')),
    verified            BOOLEAN NOT NULL DEFAULT false,
    merged_by_embedding BOOLEAN NOT NULL DEFAULT false,
    occurrence_count    BIGINT NOT NULL DEFAULT 1,
    version             BIGINT NOT NULL DEFAULT 1,
    first_seen_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_seen_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (incident_id, context_fingerprint)
);

CREATE INDEX idx_variants_incident
    ON IncidentVariants (incident_id);
CREATE INDEX idx_variants_embedding
    ON IncidentVariants
    USING hnsw (context_embedding vector_cosine_ops);

-- Solutions: versioned. One current per variant.
CREATE TABLE VariantSolutions (
    id                 UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    variant_id         UUID NOT NULL REFERENCES IncidentVariants(id) ON DELETE CASCADE,
    text               TEXT NOT NULL,
    recorded_by        TEXT,
    recorded_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    superseded_at      TIMESTAMPTZ,
    superseded_reason  TEXT,
    verified           BOOLEAN NOT NULL DEFAULT false
);

CREATE UNIQUE INDEX one_current_solution_per_variant
    ON VariantSolutions (variant_id)
    WHERE superseded_at IS NULL;

CREATE INDEX idx_solutions_variant
    ON VariantSolutions (variant_id);

-- Failures: append-only
CREATE TABLE SolutionFailures (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    variant_id    UUID NOT NULL REFERENCES IncidentVariants(id) ON DELETE CASCADE,
    solution_id   UUID REFERENCES VariantSolutions(id) ON DELETE SET NULL,
    note          TEXT,
    recorded_by   TEXT,
    recorded_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_failures_variant
    ON SolutionFailures (variant_id);

-- Links: related anchors, possibly cross-domain, possibly cross-kind
CREATE TABLE IncidentLinks (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    from_incident   UUID NOT NULL REFERENCES ProcessedIncidents(id) ON DELETE CASCADE,
    to_incident     UUID NOT NULL REFERENCES ProcessedIncidents(id) ON DELETE CASCADE,
    similarity      REAL NOT NULL,
    relation        TEXT NOT NULL DEFAULT 'related',
    kind            TEXT NOT NULL DEFAULT 'suggested'
        CHECK (kind IN ('suggested','confirmed','rejected')),
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (from_incident, to_incident)
);

CREATE INDEX idx_links_from
    ON IncidentLinks (from_incident) WHERE kind != 'rejected';
CREATE INDEX idx_links_to
    ON IncidentLinks (to_incident)   WHERE kind != 'rejected';

-- System config (generic key-value; not for per-domain data)
CREATE TABLE SystemConfig (
    key    TEXT PRIMARY KEY,
    value  TEXT NOT NULL
);

4.4 · Who does what — the full pipeline

Every component, every transformation, in order. This is the complete inventory of processing steps across the system.

STAGE 1 Edge — filter, hash, batch Go Watcher
01Read — journalctl -f → raw line
02Filter — raw line × watch configs → matched | dropped; assigns domain from the matching config
03Buffer — matched lines → per-domain 5s window
04Canonicalize — raw text × domain rules → shape_string
05Hash — shape_hash = sha256(shape_string)
06Context — fields → JSON → sorted keys → canonical string
07Fingerprint — context_fingerprint = sha256(canonical context)
08Local dedup — group by (shape_hash, fingerprint) → collapse; each group carries collapsed_count
09Assign ID — collapsed observation → stable event_id
10POST — batch → POST /ingest
Does NOT compute: embeddings  ·  Does NOT know: whether anchors exist
STAGE 2 API — re-canonicalize Ingest API
11Receive — POST /ingest → batch
12Re-canonicalize — raw text × in-memory rules → authoritative shape_hash
13Re-context — context fields → authoritative context_fingerprint
Watcher's values are ignored; the API's win. No DB access yet.
STAGE 3 Peek — read-only Ingest API
14Anchor peek — SELECT anchor by (kind, domain, shape_hash, shape_version)
15Variant peek — for each sample: SELECT variant by (anchor_id, context_fingerprint)
Purpose: determine which case (A/B/C) we're in. Writes: none.
STAGE 4 Conditional embedding Ingest API
16Shape embed — if anchor missing: embed(shape_template)
17Context embed — for each sample whose variant is missing: embed(context_canonical)
Only embed what's needed. Case A: nothing. Case B: contexts only. Case C: shape + contexts.
STAGE 5 Critical section — the only write path Ingest API
18Sort — samples by context_fingerprint (deterministic)
19Branch — Case A | B | C, then run the appropriate path (see §5)
20Commit — durability. If new anchor: NOTIFY anchor_created
Only place in the system that writes to anchors, variants, or counts.
STAGE 6 Post-commit — link creation (async) Linker
21Receive — anchor_created NOTIFY or periodic sweep (5 min)
22Rate gate — count anchors per domain in the last minute
23ANN — within kind, cross-domain allowed, same embedding model only
24Insert link — suggested links, ON CONFLICT DO NOTHING
Never blocks ingest. Backed by the periodic sweep for missed NOTIFYs.
STAGE 7 Lookup — read-only cascade Ingest API
25Receive — GET /lookup?text=...&context=...
26Canonicalize — text × rules → shape_hash
27Combined query — LEFT JOIN anchor + variant by (shape_hash, fingerprint)
28Branch — cascade (see §5.8): exact → variant KNN → anchor ANN
Read-only. Never writes.

5 The critical section

Peek first, embed conditionally, lock only on insert. Idempotency-gate every write.

The rule

Lock only when an INSERT might happen. Re-check only what you might INSERT. Updates to known rows are atomic — no lock, no re-check, no re-embed. Idempotency insert lives in the same transaction as the count increment it gates.

CASE A
Anchor exists. All fingerprints hit. Pure repeat.
lockno
embedno
re-checkno
~5msfast path
CASE B
Anchor exists. Some fingerprints miss. New context under known error.
lockyes

CASE C
Anchor missing. First time seeing this error shape.
lockyes

Thresholds (tunable)

< 0.10 → candidate same variant (increment count, set merged_by_embedding=true). 0.10–0.20 → borderline (needs_review). ≥ 0.20 → novel cause (active). These are classification heuristics, not correctness rules.

Per-incident KNN does not route through HNSW

The candidate set under one anchor is small. The planner uses idx_variants_incident and does an exact sort. The HNSW index on context_embedding exists for future global queries but is not on this path.

5.8 · The lookup cascade

Lookup is a read-only mirror of the ingest critical section. It resolves anchor and variant in one query, then fans out only as needed.

The single query — resolves the first two guards in one round trip

SELECT a.id AS anchor_id, v.id AS variant_id
FROM ProcessedIncidents a
LEFT JOIN IncidentVariants v
  ON v.incident_id = a.id
 AND v.context_fingerprint = $fp
WHERE a.kind=$kind
  AND a.domain=$domain
  AND a.shape_hash=$shape_hash
  AND a.shape_version=$shape_version;

The three-branch expression

match = fingerprint_hit ? exact_variant(row)
      : anchor_hit      ? knn_variant(row.anchor_id)
      :                   ann_anchor(embed(text))
Level 1
EXACT
guard: fingerprint hit (row has variant_id)
Return the exact variant + its current solution.
DB: 1 query embed: none ANN: none
Level 2
VARIANT
guard: anchor hit, variant miss
KNN over this anchor's variants. Embed context only.
DB: 2 queries embed: 1 (context) ANN: none
Level 3
ANCHOR
guard: no anchor at all
Embed text, ANN over anchors (LIMIT 1). Return that anchor's top variant.
DB: 2 queries embed: 1 (text) ANN: 1
Pruning

Each guard prevents the next expensive operation. fingerprint_hit → skips entire embedding path. anchor_hit → skips anchor-level embedding + ANN. No anchor → nothing to KNN against.

Response shape

{
  "found": true,
  "anchor_id": "uuid",
  "variant_id": "uuid",
  "solution": "systemctl start postgres",
  "distance": 0.08,
  "verified": true
}
FieldMeaning
foundfalse if nothing matched
anchor_idset if anchor matched (exact or via ANN)
variant_idset if variant resolved; null if anchor known but no variant matched
solutioncurrent solution text, if variant resolved and has one
distancenull for exact match; 0.0–0.20 for semantic
verifiedtrue if the current solution was human-verified
One threshold: 0.20

Ingest uses 0.10 / 0.20 because it's deciding (match / needs_review / new). Lookup uses 0.20 because it's retrieving (found / not found). Different operations, same cutoff number.

Case 2 at lookup time

When a query's wording differs enough to produce a new shape_hash, the anchor-level ANN surfaces the related anchor's solution immediately — not after the linker's next pass. This is what makes Case 2 work on the first lookup of a new wording.

Query embedding cache. Keyed on sha256(text + active_model). LRU ~1000 entries. Repeat lookups of the same unfamiliar wording skip the model call.

6 Canonicalization & shape hashing

rules:
  - pattern: "/dev/sd[a-z]"
    replace: "<DEV>"
  - pattern: "pid [0-9]+"
    replace: "pid <PID>"
  - pattern: "0x[0-9a-fA-F]+"
    replace: "<HEX>"
shape_string = apply_rules(canonical_error_line)
             | canonical_error_line   -- if no rule matches
shape_hash   = sha256(shape_string)

Same input + same rules → same hash, always. shape_version is per-domain — it lives on Domains.shape_version. Bumped when a domain's rule set changes.

Dual-layer design

Deterministic hashing collapses structurally similar text into anchors. Semantic linking bridges anchors that are textually distinct but conceptually related. Both layers are necessary.

7 Context (the variant key)

PathFields

context_canonical   = JSON.stringify(context_json, keys_sorted)

Fingerprint vs. variant

A context fingerprint is an exact identifier. A variant is a semantic cause group. Multiple fingerprints may map to one variant when the KNN gate finds them close enough. When that happens, occurrence_count absorbs the new count and merged_by_embedding is set for audit.

8 Solution versioning (Case 3b)

BEGIN;

UPDATE VariantSolutions
SET superseded_at = now(),
    superseded_reason = $reason
WHERE variant_id = $variant_id
  AND superseded_at IS NULL
  AND id = $expected_solution_id;

rows = ROW_COUNT;
IF rows = 0 AND $expected_solution_id IS NOT NULL:
    ROLLBACK;
    RETURN 409 CONFLICT;

INSERT INTO VariantSolutions (variant_id, text, recorded_by, verified)
VALUES ($variant_id, $text, $recorded_by, false);

COMMIT;
No advisory lock needed

The partial unique index and conditional supersede handle concurrency. Lost updates return 409.

9 Linking (Case 2)

Runs post-commit. Triggered by NOTIFY anchor_created. Backed up by a periodic sweep.

Fast path — NOTIFY

On notification: fetch anchor, rate-gate per domain, ANN within kind, insert suggested links.

Backstop — periodic sweep

Every 5 minutes: find anchors created since last checkpoint with no outgoing link, process them the same way, advance the checkpoint.

Links vs. lookup ANN

Both find related anchors, but they serve different purposes:

Lookup ANNLinks
WhenOn demandPersistent
PurposeFind the answer to this queryBrowse "anchors related to X"
CostOne ANN queryJoin or scan
ConsumersAgent/links, UI

Lookup does not traverse IncidentLinks. The ANN fallback in §5.8 covers the retrieval need directly. Links exist for browsing and review.

14 Invariants

  1. 01HTTP idempotency. Every observation has a stable event_id. Count increments are paired with a ProcessedIngests insert in the same transaction.
  2. 02Determinism. shape_hash is a pure function of (shape_string, shape_version).
  3. 03Deterministic batch order. Samples sorted by context_fingerprint before processing.
  4. 04Anchor uniqueness. One anchor per (kind, domain, shape_hash, shape_version).
  5. 05Variant uniqueness. One row per (incident_id, context_fingerprint).
  6. 06One current solution. Partial unique index.
  7. 07Solution concurrency. Conditional supersede + partial unique index. No lost updates.
  8. 08Bounded critical section. Lock budget 2,000ms. Timeout → 503.
  9. 09Lock only on insert. Fast path (Case A) takes no advisory lock.
  10. 10Single transaction. Winning lock attempt carries through to COMMIT.
  11. 11Post-commit notify. NOTIFY only after COMMIT, only if new.
  12. 12Linker backstop. Periodic sweep processes anchors the NOTIFY missed.
  13. 13Linking outside the lock. Linker never blocks ingest.
  14. 14Embedding outside the lock. All embedding before lock acquisition.
  15. 15Peek before embed. Known errors pay no embedding cost.
  16. 16Cross-model suppression. KNN and linking compare same-model vectors only.
  17. 17One API, many clients. MCP is not in the path of any non-agent client.
  18. 18Embedding is a candidate signal. Fingerprint hits are authoritative. Auto-merges are auditable.
  19. 19Lookup is a cascade with pruning. Exact → variant KNN → anchor ANN. Each guard prevents the next expensive operation.
  20. 20One lookup threshold. 0.20 for both variant KNN and anchor ANN.

17 What this system is not

  • Not observability. No alerting, no on-call dashboards.
  • Not a log store. Stores shapes, contexts, solutions — not raw log lines.
  • Not real-time. 5s batch + async linker + periodic sweep.
  • Not multi-user. Shared knowledge is within one machine.
  • Not durable for broadcast. LISTEN/NOTIFY is at-most-once; the sweep is the backstop.
  • Not distributed. One Postgres, one API, one watcher.

Summary

Four mechanisms: collapse (hashing), discriminate (context + embedding), relate (linking), version (solutions).

Ingest: peek first, embed conditionally, lock only on insert, idempotency-gate every write.

Lookup: three-branch cascade — exact → variant KNN → anchor ANN. One query for the first two guards, one threshold (0.20), one response shape.

One API, many clients. MCP is the agent adapter — not a gateway.

Linker is best-effort with a sweep backstop. Links are for browsing; lookup uses ANN directly.
